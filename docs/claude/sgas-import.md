`Sgas project/sgas-app/` (⚠ the repo is PUBLIC — `*.mdb` is now gitignored;

Read it with **mdbtools** (`mdb-tables`, `mdb-export`). **mdbtools is NOT

it there (28MB, well under the stage limit). It is **latin-1**, not UTF-8, and

reads the true 20,980 rows.

## What is in it
Nine tables, one that matters: **`BlankTable2`, 20,980 rows × 159 columns**, no
relationships. Each row is one person's assessment record — their details
repeated, then ~122 yes/no columns, one per qualification. About 8,300 people.
Three `ExportErrors` tables sit beside it, which is what a previous failed
import leaves behind. Chris confirms this IS the live database they use.

## THE EXPIRY COLUMNS — SOLVED 29 Aug 2026
Chris: *"the expiry is a warning they use (we will automate this but they did it
manually)… the expiry is the one furthest out, and there should be one that's 6
months prior — that's their warning to contact the client."* The data agrees,
and **the naming is backwards**:

- **`expiryfive` IS THE REAL EXPIRY.** Median 1,825 days after the assessment
  date = 5.00 years. Only 2,970 rows have it.
- **`Expirydate` IS THE WARNING.** Median 1,640 days = 4 years 6 months — six
  months before the real one. Where both exist, `expiryfive − Expirydate` is
  ~6 months on **63%** of rows and never zero. 12,327 rows have it.
- **`Exdate2` IS NOT A THIRD THING.** Where both exist it equals `Expirydate` on
  **96%** of rows (median difference 0 days). It is the same value carried for
  the second sitting.

**The catch: the warning column is the populated one.** In the seven-year scope:
1,459 have `expiryfive`, **3,243 have only `Expirydate`**, 202 have only
`Exdate2`, 124 have no expiry at all. So for about two thirds of the import the
true expiry must be DERIVED as warning + 6 months.

**Precision caveat — do not oversell it.** Only 63% are cleanly six months
apart; the rest scatter −141 to +506 days, and only 14% of `expiryfive` values
land exactly on 1826/1827 days. These are hand-typed dates centred on a rule,
not generated by one.

**RULE FOR THE IMPORT:** expiry = `expiryfive` when present, else
`Expirydate + 6 months`, else `Exdate2 + 6 months`. **Store a flag saying which**
— read from the file, or worked out — the same principle as
`staff_accreditation.expires_on` being stored rather than derived, so the
certificate's own date can always win.

**Do NOT import their warning date.** Our renewal engine computes the warning
window itself (configurable). Their manual column is evidence for the expiry,
not a value to keep. Worth defaulting the delegate renewal window to **6 months**
to match how they have always worked (it currently defaults to 90 days).

## ASSESSMENT-ONLY TAG (Chris, 6 Sep 2026) — the columns ALREADY EXISTED
Chris wants a third booking tag beside NEW and RE: **assessment only** (they
trained elsewhere or are time-served, they are buying the assessment, not the
course days). **`category.assessment_only` and `booking_category.assessment_only`
already existed in the live database, default false** — but NOTHING in `src/`
reads or writes them (`is_reassessment` is used all over `api.js`/`core.js`).
They appeared in NO .sql file anywhere in the project; migration
`20260906120000_assessment_only_columns.sql` is the retrospective record, written
6 Sep. The remaining work is UI + write path, not schema.

**Keep it as two booleans, not one three-way enum.** `is_reassessment` says
WHICH ticket it is; `assessment_only` says WHAT THEY BOUGHT. Both combinations
are real — a brand-new candidate can be assessment-only, and a reassessment
nearly always is. A single enum would force a false choice.
Knock-ons when it is built: **price** (assessment-only is a different price —
`category.price` is still empty on all 110 categories) and **days attended**
(`booking.attend_from`/`attend_to` already exist and are the right place for a
short attendance).

**`app_import_apply` — the step that makes decisions real.** Added 6 Sep because
the decisions were recorded intentions only: all 109 employer creates and both
Callon Fielding rows had `target_id` NULL and `company` was still on 10 rows.
It is idempotent (a row with a target_id is skipped), it groups by
`lower(btrim(target_code))` so two rows sharing a name become ONE record — the
whole "EDINA"/"EDINA UK LTD" merge story — and **only `create` rows may create**:
a `map` row naming something that is not there is left unresolved and counted,
so a mistyped map surfaces instead of spawning a duplicate. New staff are made
as PAST staff dated `current_date` (a placeholder for "not here any more", so
they stay out of the booking dropdowns). Created qualifications land in scheme
'Other' so they show up on Courses asking to be filed.

## Not built yet

   in-scope rows with expiry resolved by the rule above plus the source flag.
2. **Staging table + load.** SQL inserts through the MCP is too many tokens; the

   keyboard) or a service-key upload.
3. **Person matching** (N1 exact → name+DOB exact → fuzzy → review queue) is

   fuzzy is genuinely needed. 3,225 rows have neither N1 nor name+DOB and cannot
   be attributed at all; 96 N1 numbers carry more than one surname.
4. A dry-run count before commit, and a review screen for the fuzzy queue.

## UI rules Chris asked for, and they are the point
- **The suggestion is already in the dropdown** — the job is to press Confirm,
  not to hunt down a list of 110.
- **Nothing saves until Confirm.** A box that fills itself in and saves itself
  is a guess with extra steps.
- **Create takes OUR name, not theirs** — a text field beside the dropdown,
  prefilled from the suggestion, so a renamed course gets the right name.
- **Two rows created under the same name become one thing.** No merge UI needed.
- `app_import_accept_proposals` is kind-aware: a suggestion means `map` for
  qualifications and staff, `create` for employers.
